# Date/Time Persistence Audit

## Story

Review every date/time definition and database persistence path after the business-timezone month-filter work, identifying any remaining host-timezone dependence, ambiguous date conversion, or schema weakness that could make stored records or date queries inconsistent.

## Acceptance Criteria

- Inventory every persisted date field and application-generated timestamp.
- Confirm ordinary timestamps remain UTC instants and business-calendar values use `BUSINESS_TIMEZONE`.
- Identify date parsing, request handling, schema, and presentation paths that still depend on the runtime host timezone or accept ambiguous values.
- Separate current database risks from API/display-only risks and future auditability concerns.

## Findings

### Medium: `failureInfo.timestamp` is not schema-enforced as a BSON Date

`Guide.failureInfo` is declared as `@Prop({ type: Object })`, while only its TypeScript annotation describes `timestamp: Date` (`src/guides/entities/guide.entity.ts:136-142`). Current service writes consistently assign `new Date()` (`src/guides/services/guides-db.service.ts:154-183`, `src/guides/services/guides-db.service.ts:605-612`, `src/guides/services/guides-db.service.ts:701-710`), so existing application writes are correct.

The mixed object nevertheless allows a future or direct update to store an offset-free string, localized text, or another non-Date value without Mongoose casting or validation. Retry attempts and comments use typed sub-schemas and do not have this weakness (`src/guides/entities/guide.entity.ts:56-79`).

### Medium: balance-request email dates use the host timezone

The balance-request email calls `createdAt.toLocaleDateString('es-MX')` without a `timeZone` option (`emails/BalanceRequestCreated.tsx:25-49`). Locale controls formatting, not timezone. The same stored instant can therefore render as different calendar dates in Lambda and on a developer machine near Mexico City midnight.

The DB record and API response remain correct UTC instants. This is a presentation inconsistency, and the email payload/template currently has no business-timezone input (`src/balance/services/balance.service.ts:477-492`, `src/mail/services/mail.service.ts:51-59`).

### Low: provider timestamps have ambiguous runtime contracts

- Manuable accepts `created_at` as an unrestricted string and parses it through `new Date(string)` (`src/manuable/manuable.interface.ts:142-155`, `src/manuable/manuable.utils.ts:151-173`). Offset-free values depend on native runtime parsing, and malformed values become invalid dates.
- Pakke types JSON date fields as `Date` and forwards `CreatedAt` without runtime conversion (`src/pakke/pakke.interface.ts:205-224`, `src/pakke/pakke.utils.ts:151-173`). Axios normally returns JSON strings, while tests construct actual `Date` objects.
- T1 documents an offset-free provider timestamp but currently does not map it into the common response (`src/t1/t1.interface.ts:64-72`, `src/t1/t1.utils.ts:223-234`).

These provider timestamps are not currently persisted into `Guide`; persisted guide `createdAt` is generated by Mongoose. They are API-output risks and would become persistence risks only if later copied into Mongo without a provider-specific offset/timezone contract.

### Low: adjacent date-filter validation is inconsistent

- Guide `year` uses `@IsNumber()` without integer or minimum constraints, unlike balance `year` (`src/guides/dtos/guides-db.dto.ts:85-89`, `src/balance/dtos/balance.dto.ts:48-53`). Luxon rejects invalid calendar construction, but the input contract is weaker than intended.
- Explicit guide ranges do not reject `startDate > endDate`; they produce an empty Mongo range (`src/guides/services/guides-db.service.ts:781-790`).
- Explicit ranges use inclusive `$lte` for `endDate`, while month ranges use exclusive `$lt` for next-month midnight (`src/guides/services/guides-db.service.ts:788-799`). This is not timezone-dependent, but clients need to understand the differing boundary semantics.

## Confirmed-Compliant Persistence

- Guides, balances, and balance requests use Mongoose timestamps, which create ordinary `Date` instants (`src/guides/entities/guide.entity.ts:81-84`, `src/balance/entities/balance.entity.ts:4-19`, `src/balance/entities/balance-request.entity.ts:9-50`).
- Retry, failure, sync, comment, debit, decision, deletion, and counter-update timestamps use zero-argument `new Date()` or `Date.now()`. These represent instants and must not be localized before persistence.
- Retry cooldown uses epoch-millisecond arithmetic and is timezone-independent (`src/guides/services/guides-db.service.ts:377-387`).
- Guide and balance month queries use configured-zone local month boundaries converted to UTC and half-open `$gte`/`$lt` ranges (`src/date-time/date-time.utils.ts:24-67`).
- Although neither bootstrap sets `ValidationPipe({ transform: true })`, the installed Nest 11 pipe returns the transformed plain object when validator options such as `whitelist` are present. The DTO `@Type(() => Number)` decorators therefore supply numeric month/year values to the services (`src/main.ts:25-30`, `lambda.ts:29-34`, `src/guides/dtos/guides-db.dto.ts:77-89`, `src/balance/dtos/balance.dto.ts:39-67`). There is no HTTP-level regression test for this framework-dependent behavior.
- Kraft IDs derive `YYYYMM` from the configured business zone (`src/guides/services/guides-db.service.ts:880-893`). Counter `createdAt`/`updatedAt` fields remain ordinary UTC-representable instants (`src/guides/entities/kraft-id-counter.entity.ts:4-16`).
- Explicit guide date filters reject date-only and offset-free strings and normalize accepted values to UTC (`src/guides/dtos/guides-db.dto.ts:53-75`, `src/date-time/date-time.utils.ts:79-92`).
- Date response fields remain `Date` values and serialize as UTC ISO strings; no response-localization path was found in guide or balance services.
- No component-based `new Date(year, month, day)`, local `Date` getters/setters, Mongo `$date*` aggregation, TTL date index, timestamp hook, custom Mongoose clock, or process-level `TZ` dependency remains in production persistence code.

## Configuration Assessment

`BUSINESS_TIMEZONE` is required and validated as a named IANA zone (`src/app.module.ts:28-40`, `src/config.validation.ts:4-17`), exposed through typed config (`src/config.ts:18,87-89`), and forwarded by production and stage Serverless definitions (`serverless.yml:12-15`, `serverless.stage.yml:12-15`). `.env-example` includes the intended value (`.env-example:1-3`).

No additional timezone configuration is needed when creating ordinary records. Adding process-level `TZ` or converting current timestamps to business-local wall time would make persistence less reliable. Deployment still depends on the external environment actually supplying the configured value; static repository review cannot verify deployed secrets or Lambda configuration.

## Schema Coverage and Auditability

Users, addresses, provider-token configuration, and global configuration do not enable Mongoose timestamps (`src/users/entities/users.entity.ts:5-45`, `src/addresses/entities/addresses.entity.ts:4-43`, `src/general-info-db/entities/general-info-db.entity.ts:12-28`, `src/global-configs/entities/global-configs.entity.ts:29-45`). This does not create timezone inconsistency because those collections define no date fields. It is an auditability/product-policy question if record creation/update history is required later, not a missing timezone setting.

## Dependencies and Integration Points

- Nest `ValidationPipe` and class-transformer determine the runtime query types reaching the shared Luxon utility.
- Mongoose schema casting determines whether nested timestamps are guaranteed to be BSON dates.
- React Email formatting determines the business-calendar date visible to administrators.
- Provider API contracts determine whether external timestamps represent explicit instants.

## Edge Cases and Constraints

- Records around local midnight must keep the same stored UTC instant while business-calendar IDs, filters, and displays select the configured local date.
- Provider offset-free timestamps cannot be safely assigned a timezone without a documented provider contract.
- Existing Mongo data may contain legacy field types that static schema review cannot detect, especially under mixed fields such as `failureInfo`.
- Live Mongo index definitions and direct writes outside this application were not observable from repository source.

## Open Questions

- Should balance-request emails display dates in `BUSINESS_TIMEZONE`, or is UTC intentionally acceptable for operational email?
- Do Manuable and Pakke guarantee offsets in their timestamp payloads, and what timezone does T1's offset-free timestamp represent?
- Is creation/update auditing required for users, addresses, provider configuration, and global configuration?

## Assumptions

- MongoDB stores Mongoose `Date` values as BSON UTC instants.
- Persisted guide creation time is the application's record-creation instant, not the provider's creation time.
- No untracked external writer inserts localized strings into date-bearing fields.
